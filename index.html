Overview

What this is, and what it is not

Built as a cumulative 15-phase roadmap. Each phase leaves the repository in a coherent, demoable state and builds on the last rather than bolting on beside it.

◎ The problem

An application team should ship a service without knowing how ingress, TLS, autoscaling, network policy, secret management or tracing work. A platform team should be able to guarantee every shipped service has all of them, correctly, by default.

⬢ The approach

Guardrails that reject unsafe configuration at admission rather than catching it in review. Missing resource limits, unsigned images and :latest tags are refused by the cluster, not by a reviewer having a good day.

◆ Honest status

Nothing here is described as done before it is. Phase 1 works and is verified end to end; the other fourteen are documented scaffolding with acceptance criteria written in advance, so progress is measurable rather than asserted.

✕ Deliberate exclusions

Service mesh, multi-cloud and multi-cluster are excluded on purpose, each with a written reason. What you leave out is a design decision too — and defending an exclusion is harder than adding a logo to a diagram.

Quick start

Cluster in one command

Requires Docker (4 GiB+), kind, kubectl and make. make preflight checks all of it and names anything missing.

bash 
# clone and boot
git clone https://github.com/sameeralam3127/kubernetes-platform.git
cd kubernetes-platform

make preflight   # verify your toolchain
make up          # create the cluster (1-3 min)
make status      # confirm healthy
make down        # tear it all down

✓ What you get

A three-node cluster — one control plane, two workers. Two workers rather than one because PodDisruptionBudgets, pod anti-affinity, topology spread and the Phase 12 node-drain experiment are all no-ops on a single node.

1 control-plane 2 workers zones local-a / local-b ports 80 · 443 · 30000 loopback only

↻ Idempotent by design

make up twice is a no-op, and it refuses to report success on a half-built cluster — it probes the API server rather than trusting that the cluster is merely listed. A partial kind create leaves containers behind that would otherwise look healthy.

⛨ Safe teardown

Teardown is scoped by kind cluster name, so it is structurally incapable of touching a real cluster. It still warns when your current context points somewhere unexpected — a surprised operator is worth catching even when nothing is at risk.
